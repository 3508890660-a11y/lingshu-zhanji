# 灵枢战纪 · 观战台 v0.1

> 一套「**无头规则引擎 + 脚本 AI + 事件回放**」的卡牌对战小游戏。
> 卡池直接由 `灵枢战纪/卡包/第一弹_灵枢觉醒_卡表.md` 生成——**卡表改了，重跑一条命令，游戏里的卡就跟着改**。

---

## 1. 运行

```bash
cd "EX4以自创card game为主题/game_lq01"
node server.mjs          # 或 npm start
# 浏览器打开 http://127.0.0.1:5173/
```

- 零依赖：不需要 `npm install`，只用 Node 内置模块。
- **必须走 http**，不能双击 `index.html`——ES Module 在 `file://` 下会被 CORS 拦掉。
- 无头自检：`node tools/smoke.mjs`（跑 96 局，校验能否正常结束 + 复现性）。

## 3. 整体架构

### 3.1 三层，一条单向数据流

```
             ┌──────────────────────────────────────────┐
  卡表.md ──▶│ tools/gen_cards.mjs                      │
             │  正则解析 → 效果 DSL → cards.gen.js       │
             └──────────────────────────────────────────┘
                              │
                              ▼
  脚本 build(pool) ──▶ 卡组 ──▶ ┌───────────────────────┐
                                │  rules.js（无头）      │
  choose(view,moves) ◀──────────│  逐动作推进，产出      │
                                │  steps[] = 事件+快照   │
                                └───────────────────────┘
                                            │
                                            ▼
                                ┌───────────────────────┐
                                │  app.js（观战台）      │
                                │  只按索引渲染快照      │
                                └───────────────────────┘
```

**关键决定：整局先跑完，再回放。**

这不是"为了好看"，而是三个工程上的必然：

1. **暂停 / 单步 / 调速不影响对局**。播放器只是在 `steps[]` 上移动指针，不存在"暂停时引擎还在跑"的竞态。
2. **脚本是同步的**。`choose(view, moves)` 立刻返回一个动作，不需要 async/await、不需要处理"玩家中途关页面"。
3. **可复现**。`(卡组, 脚本, 种子)` 三元组唯一确定一局；测试里就是靠这条做回归。

代价是内存里存了整局的快照。实测一局 50~130 步，每步两个玩家的场面，量级在几十 KB，可以忽略。

### 3.2 模块依赖

```
rules.js  ← 只依赖 cards.gen.js
builtin.js ← 只依赖 deckbuild.js（不 import rules，避免循环）
app.js    ← 依赖三者
```

`rules.js` 不认识"AI"这个概念——它只要求传入的对象有 `choose(view, moves)`。所以内置 AI 和用户脚本在引擎眼里是同一类东西。

## 4. 脚本接口设计

### 4.1 契约

一段脚本就是一个声明了 `build` 与 `choose` 的 JS 源码：

```js
const meta = { name: '我的脚本', desc: '一句话' };

function build(pool) { /* 可选：返回 [{id,n}] 或 '3x LQ01-037' */ }
function choose(view, moves) { /* 必填：返回 moves 里的某一个 */ }
```

编译方式（`js/ai/loader.js`）：

```js
new Function('api', src + '; return {build, choose, meta}')
```

`api` 里注入了 `CARDS / scoreCard / autoBuild / byId / costOf`，脚本不必自己 import。

### 4.2 `view` —— 只读快照

```ts
{
  turn: number, round: number, active: 0|1,
  me: {
    color, life, res, resName,
    hand: [{ id, name, type, cost:{k,n}, atk, imp, hp, kw, effects, text, sr }],
    board: [{ uid, name, atk, imp, hp, maxHp, kw, frozen, attacked, equips }],
    lands: string[], deck, grave, plays
  },
  opp: { color, life, res, resName, handCount, board, lands, deck, grave }
}
```

- `me.hand` 是**完整卡面**（含 `effects`），脚本可以自己做价值判断；
- `opp.handCount` 而不是 `opp.hand`——**对手手牌不可见**。这是给"信息不完全"留的口子，也是脚本不能偷看底牌的结构保证。

### 4.3 `moves` —— 合法动作全集

```ts
{ type:'play',   i: 手牌下标, target?: uid }   // target 只有需要指定目标的卡才有
{ type:'attack', uid: 攻击者, target: uid | 'face' }
{ type:'pass' }
```

**为什么是"枚举 + 选择"，而不是"让脚本调用 API"？**

| 方案 | 脚本要做什么 | 引擎要做什么 | 作弊面 |
|---|---|---|---|
| 脚本调 API（`game.play(card)`） | 自己判断能不能打、够不够费、目标合不合法 | 每一步都要防御非法调用 | 大：漏一个校验就能凭空出牌 |
| **枚举 + 选择（本实现）** | **只排序、只挑一个** | 开局就把非法动作全部排除 | **零**：不在 `moves` 里的东西脚本给不出来 |

代价是脚本表达力受限于引擎给的粒度（比如没法"先横置再宣告"这种复合动作）。对这个体量的游戏，这个交换是划算的。

### 4.4 组卡接口

`build(pool)` 收到的是**已经过滤过的卡池**：

```ts
pool: [{ id, name, type, cost, atk, imp, hp, kw, effects, rare, score }]
```

- `score` 是 `deckbuild.js` 给的粗评分，方便"懒得写"的脚本直接用；
- 返回值可以是结构化数组，也可以是 `3x LQ01-037` 这样的文本；
- 返回 `null` 或抛异常 → 引擎回退到 `autoBuild`（保证"脚本写坏了也能开局"）；
- 组出来的卡组会过一次 `validateDeck`：**25~40 张**（比正式规则的 30~40 略宽，方便脚本试卡组）、同名牌 ≤3、不能混色（灰色除外）。**不合规就回退**，不会出现一副 60 张的怪物。

### 4.5 错误处理

三层兜底，任何一层出问题都不会让对局卡死：

1. `build` 抛异常 → 自动组卡；
2. `choose` 抛异常 → 记录一条 `※ 脚本异常` 日志 → 该步按 `pass` 处理；
3. `choose` 返回了一个不在 `moves` 里的动作（结构不匹配）→ 同样按 `pass`。

### 4.6 最小可用脚本（可直接粘进编辑器）

```js
const meta = { name: '打脸机', desc: '有牌就出，能打脸就打脸' };

function choose(view, moves) {
  const plays = moves.filter(m => m.type === 'play');
  if (plays.length) return plays[0];                 // 先出牌
  const face = moves.filter(m => m.type === 'attack' && m.target === 'face');
  if (face.length) return face[0];                   // 再打脸
  return moves[moves.length - 1];                    // 否则结束回合
}
```

## 5. 对局流程

### 5.1 回合状态机

```
开局：双方各抽 4 张 → 先手方 start
                    │
   ┌────────────────▼─────────────────┐
   │ start 阶段                        │
   │  1. 重置 attacked / frozen / temp │
   │  2. 粉色：0.7 概率骑升（上限 Lv4）│
   │  3. 刷新资源（按色规则，见 5.2）  │
   │  4. 成长 / 再生结算               │
   │  5. 抽牌（按色规则）              │
   └────────────────┬─────────────────┘
                    ▼
   ┌──────────────────────────────────┐
   │ main 阶段（循环）                 │
   │  moves = legalMoves()             │
   │  mv = script.choose(view, moves)  │
   │  apply(mv) → 记录一步（事件+快照）│
   │  mv.type === 'pass' → 结束回合    │
   └────────────────┬─────────────────┘
                    ▼
   ┌──────────────────────────────────┐
   │ end 阶段                          │
   │  1. 弃至 7 张                     │
   │  2. 按色补牌（红/绿/银/金）        │
   │  3. 清空本回合 buff               │
   │  4. 交换行动方；满 20 轮起灼烧    │
   └──────────────────────────────────┘
```

### 5.2 十一色资源表（本版实装口径）

| 色 | 资源 | 起始/成长 | 消耗 | 抽牌 |
|---|---|---|---|---|
| 白 | AP | 3 点；T5 起 4、T9 起 5 | 消耗 | 回合开始 1 |
| 黑 | 牺牲 | `2 + ⌊回合/2⌋` | 消耗 | 回合开始 1 |
| 红 | 激情 | `min(2×回合, 10)` | **门槛不消耗** | 回合开始 0；结束补至 `(10−激情)÷2` |
| 绿 | 法力 | `2 + 地标数` | 消耗 | 结束补至 `地标数+1` |
| 蓝 | 手牌 | ＝当前手牌数（动态） | **门槛不消耗** | 回合开始 2 |
| 紫 | 灵脉 | 每回合投 `min(3+⌊回合/3⌋, 6)` 枚 D6 求和 | 消耗 | 回合开始 1 |
| 橙 | 锻造 | `2 + 装备数×2` | 消耗 | 回合开始 2 |
| 青 | 法力 | `min(回合+1, 6)` | 消耗 | 回合开始 2 |
| 银 | 共鸣 | ＝场上卡牌数（**下限 1**） | **门槛不消耗** | 结束补至 `min(max(共鸣,3),5)` |
| 粉 | 灵压 | `0/2/4/6/8`（骑升 0.7）（**下限 1**） | **门槛不消耗**，每回合限打 2 张 | 回合开始 1 |
| 金 | 金币 | 每回合 2 基础 + 金币卡产出 | 消耗 | 结束补至 5 |
| 灰 | 继承 | 用主色资源付 `通用N` | 视主色 | — |

> **下限 1 是必要的**：银的共鸣＝场上卡牌数、粉的灵压 Lv0＝0，若不设下限，这两色在开局第 1 回合**一张牌都打不出**（所有卡门槛都 ≥1），会直接死锁。这是实现层的必要修正，不是设计改动。

### 5.3 战斗结算（按规则书 3.3）

```
宣告攻击 → 守卫检查（有守卫则只能打守卫）
        ├─ 目标＝灵体：IMP 直击，扣生命
        └─ 目标＝单位：互以 ATK 同时结算（守护X 减伤 → 圣盾抵消 → 扣耐久）
                      双方同时判死，再统一离场（避免"先死者先离场"改变另一方判定）
        践踏：溢出伤害转脸
        疾风：攻击结算后追加 1 点
```

### 5.4 胜负

- **生命 ＝ 生命卡组剩余张数**（初始 20）。受伤时逐张把生命卡从卡组顶移入损伤区，被移出的特效卡各触发一次——这就是编外卡 `SM01` 的实装方式。
- 生命 ≤ 0 判负；双方同时 ≤ 0 判平。
- 牌库抽空：疲劳递增伤害（1、2、3……）。
- **第 20 轮起双方每回合各受 2 点灼烧**，保证任何对局都会在有限步内结束（灰镜像实测 49 回合判平）。

> **为什么要真做生命卡而不是"20 点血"**：生命卡如果有特效，"挨打"就不是纯亏损——红的【殉道血誓】会让你在濒死时反打 2 点，蓝的【逆流书签】会把攻击者弹回手牌。这套"受伤即资源"的张力是这个游戏的身份，抽象成一个数字就没了。

> **v3.3-3 的四条口径订正**（每一条都改变了实测结果，见 §10）：
> 1. **外枢灵体不进弃牌区**：它是额外卡组的卡，落进弃牌区就会被重构洗回牌库、变成抽到也打不出的死卡。现在被破坏／回手／献祭一律回外枢区（`used` 复位，可再升灵）。
> 2. **蓝的门槛实时结算**：蓝的资源＝当前手牌数，打一张牌手牌 −1 ⇒ 门槛自然下降，这本来就是它的自限；快照等于把闸门冻在最高点。
> 3. **蓝的打出上限 3 → 2**：蓝是唯一"回合抽 2 ＋ 手牌无上限"的颜色，8 回合后手牌 10 张以上、任何费用都免费。3 张时蓝 85%，2 张时 58%。
> 4. **金是 DBG**：购买入弃牌区、回合末弃光重抽 5、重构免费。缺任何一条，"10 张固定牌＋购入牌"的循环就不成立。

### 5.7 灵体卡（33 张）

每方开局带 1 张灵体，**不属于主卡组**，常驻灵体区。它在引擎里是一个挂在玩家身上的对象，提供一条**被动**（6 类钩子）与一条**启动能力**（每回合 1 次）。

| 钩子 | 触发点 | 用在谁身上 |
|---|---|---|
| `auraAtk` / `auraHp` / `auraKw` | 你的单位**进场时**加身材／关键词 | 拉格纳（冲锋）、奥蕾莉亚（守护1）、诺娃（守卫）… |
| `turnStartRes` / `turnStartDraw` / `turnStartToken` | 你的回合开始 | 盖亚、克罗诺、摩根… |
| `lifeDraw` | 你的生命卡移入损伤区 | 塞西莉亚 |
| `damagedAtk` | 你的单位每次受伤 | 莫德里斯 |
| `deathDraw` / `deathRes` | 你的单位被破坏 | 泽拉斯、莫尔菲斯、莉莉丝 |
| `diceBonus` | 紫的骰池投掷数 | 卡奥斯 |
| `enterAtk` / `secondCardDraw` | 你打出一张牌之后 | 卡恩、泽菲 |

**启动能力**统一走 `{type:'avatar'}` 这个动作：
- 每回合 1 次，**不带目标**（避免再引入一个指向选择）；
- 费用按该色资源：数值型（白AP／黑牺牲／绿·青法力／紫灵脉／橙锻造／金金币／红激情）照扣，**蓝／银／粉是动态门槛，只判不扣**；
- 时机由 `timing` 决定：**只有"本回合有效"的群体增益（拉格纳的 IMP+1）留到出完牌再开**，其余一律开局先开——否则 AI 会把资源全花在卡上，永远开不出技能。

> 这是"AI 能不能用出这张卡"的关键设计：**技能若与卡牌抢同一份资源，就必须允许它先于卡牌结算**，否则再强的灵体在自动对局里也是摆设。

## 6. 观战界面实现

### 6.1 快照，而不是增量

每执行一个动作，引擎推一条：

```js
{ text: '赤潮 打出【怒火新兵】（激情 2）\n　【怒火新兵】登场 2/1/1', snap: {...} }
```

`snap` 是**渲染所需的全部信息**（双方生命/资源/手牌/场面/牌库数 + 回合与行动方）。

- 好处：UI 不需要"重放引擎"，也不需要维护一份镜像状态机——**渲染就是 `render(snap)`**；
- 代价：每步都要序列化一次。实测一局 50~130 步，完全可以接受。

### 6.2 播放器

```js
S.steps = res.steps;   // 整局
S.idx = 0;
function stepForward() { S.idx++; render(S.idx); }
function play() { S.timer = setTimeout(tick, 900 / S.speed); }
```

- 「播放 / 暂停 / 单步 / 速度」**只改 `S.idx`**，不触碰引擎；
- 「重来」= 用同一种子重新 `playMatch`，所以**重来看到的是同一局**（方便复盘某一步）；
- 改种子 = 换一局。

### 6.3 渲染

```
#p0 / #p1   两侧面板：生命 / 资源 / 牌库 / 手牌 / 场面 / 地标
.center     回合指示 + 战斗日志
```

- 手牌**双方都明牌**（观战视角），鼠标悬停显示卡面文本；
- 场面单位为小卡：`ATK / IMP / 耐久` + 关键词标签 + 装备数；已攻击的显示为半透明（`tapped`），被冻结的加蓝框；
- 日志按行分类着色：`turn`（回合分隔）/ `play`（出牌）/ `dmg`（伤害）/ `kill`（破坏）/ `end`（结束），颜色由 `classify()` 正则判定；
- 日志采用**增量追加 + 回退重建**：前进一步只 append，后退则清空重建。

### 6.4 组卡面板与脚本编辑器

- **卡组面板**：左右各一个 `textarea`，支持 `3x LQ01-037` 逐行。输入即校验，底部实时显示「30 张 · 红 · 10 个名目」或具体错误。右上角的下拉框可以**一键载入 11 副预组之一**，同时把颜色选择同步过去。
- **「按脚本重建」**：调用当前脚本的 `build()`，把结果写回文本框——**你可以先让脚本组卡，再手动改两张**。
- **脚本面板**：编辑器 + 脚本名输入 + 「保存并加载」。保存前先 `compileScript` 试编译，编译不过不落盘。脚本存 `localStorage`（`lq01.userScripts.v1`），下拉框里带「（我的）」后缀。
- **载入模型脚本**：点「载入模型脚本」从 `agents/agents.json` 读取 12 份模型脚本，`compileScript` 编译后直接进入左右下拉框（带「（模型）」后缀，只进内存、不写 localStorage）。选中后颜色会自动同步到脚本的 `meta.color`。
- 运行顺序：**手写卡组优先**；文本框为空或不合法时才用脚本的 `build()`，再不行用自动组卡。

### 6.5 组卡器（「组卡」页）

文本框能组卡，但不算"自由组卡"——所以另做了一个真的组卡器：

```
┌ 卡池 231 张 ─────────────┐ ┌ 卡组 30 张 · 10 名目 ──────┐
│ 搜卡名 / 色 / 类型 / 费用 │ │ 费用曲线 ▁▃▅▂▁            │
│ ▸ AP1 圣光新兵 1/1/1  ×3 │ │ ×3 圣光新兵          [−]  │
│ ▸ AP2 团结轻骑 2/1/2  ×3 │ │ ×3 团结轻骑          [−]  │
│ …（点一下 +1，同名封顶 3）│ │ …                        │
└──────────────────────────┘ └ 30 张 · 白 · 10 名目 ✓ ───┘
```

- **筛选**：卡名/编号搜索 ＋ 色 ＋ 类型 ＋ 费用，四个条件正交；
- **加卡**：点卡池行 +1，到 3 张变灰；**减卡**：卡组行右侧 `−`；
- **实时校验**：张数 25~40、同名牌 ≤3、不能混色（灰除外），底部直接显示错误原因；
- **费用曲线**：按 1~7+ 分桶画柱，一眼看出是快攻还是中速；
- **近似标记**：卡池行尾的 `⚠` 表示这张卡在引擎里是近似实现，鼠标悬停看卡面原文；
- **载入**：「载入左方 / 载入右方」把当前卡组写进对应文本框并同步颜色——**组完立刻能打，不用手抄卡号**。

> **为什么仍然保留文本框**：脚本的 `build()` 返回的是卡号列表，手写/粘贴比点选快；两种入口写的是同一份状态，谁也不挡谁。

## 7. 卡池管线

### 7.1 md → DSL

`tools/gen_cards.mjs` 读卡表，按列取 `编号/卡名/类型/费用/身材/SR/效果/稀有度`，再用一组有序正则把中文效果翻成 DSL：

| 卡面写法 | DSL |
|---|---|
| 对 1 个单位造成 3 点伤害 | `{do:'dmg', n:3, target:'enemyUnit'}` |
| 对所有敌方单位造成 2 点伤害 | `{do:'aoe', n:2, side:'enemy'}` |
| 抽 2 | `{do:'draw', n:2}` |
| 生成 2 个「士兵」衍生物（1/1/1） | `{do:'token', n:2, atk:1, imp:1, hp:1}` |
| 获得「守护2」 | `{do:'grant', kw:'守护2'}` |
| 你的单位 +0/+1 | `{do:'buffAll', atk:0, hp:1}` |
| 破坏 1 个单位 | `{do:'destroy'}` |
| 冻结 / 返回手牌 / 磨牌 / 产 N 点 | `freeze` / `bounce` / `mill` / `res` |

解析器覆盖不到的卡有两种处理：单位／地标／装备**保留身材照常可用**；法术／瞬间／结界若一条效果都没解析出来，标 `unsupported` 并从卡池剔除。

## 8. 已知边界与下一步

**边界**

- 没有阻挡宣告（规则书 3.3 允许灵体被攻击时由 1 个单位阻挡）。当前只做了守卫强制与守护减伤。
- 灰是"泛用池"不是"第十二色"，灰镜像会打成平局（双方都靠灼烧同归于尽）。
- 脚本没有真正的安全沙箱——它跑在页面主线程里。对本地单人工具够用，**不要加载来路不明的脚本**。

**下一步可以做的**

1. 把 `choose` 的粒度细化到"响应窗口"（阻挡、反击、瞬间），引擎需要引入**优先级栈**；
2. 给脚本加一个 `onEvent(ev)` 钩子，让 AI 能做"记牌"；
3. 把 `steps[]` 落盘成 JSON，做**对局库**与"按卡组检索战报"；
4. 用同一套 `moves` 接口接一个人工操作层——观战台就能变成对战台。

**预组循环赛（11 副 × 每对 8 局 = 440 局）**

|---|---|---|---|

| 橙 | 5% | 6.3 | **6/30** |

> **两个结论，都必须说清楚**：
> 1. **胜负与"单位数"高度相关**：垫底的 绿（6 单位）、橙（6 单位）正好是全表单位最少的两个预组。它们的 6 张色内通用里只有 1~2 张是单位，其余是地标／法术——**铺不出场面就既不能攻也不能挡**。
> 2. **银的 96% 不是"强"，是"没有闸门"**：它的 30 张里 27 张是共鸣 1~3，场上站到 5 张后每回合几乎能把整手牌免费打完（门槛制不消耗资源），手牌还补到 5。这是**卡池结构**问题，不是引擎漏了规则。
>
> 这两条都指向同一件事：**卡表的"每色 18 ＝ 通用 6 ＋ 流派 4×3"保证了套数，没保证类型配比**。要修必须动卡表的构成（例如规定"色内通用 6 至少含 3 张单位"），这属于设计改动，需要拍板。
